# Cluster 4: hamr-infra — Optimization Report (2026-07-01 round 2)
Replaces: `.iter-skill/runs/2026-06-30/06-dev-infra.md` (which assumed Taskfile + `.sops.yaml` + `tofu/` + `argocd/appset.yaml` + `.github/workflows/*` — **none of those exist** in the real repo)

## Executive Summary

- **Real `hamr-infra` is a plain bash + docker-compose ops repo** — 27 files, 0 IaC, 0 GitOps, 0 Helm, 0 CI workflows, 0 SOPS/Vault, 0 cosign/trivy. The round-1 picture of an "Opentofu + ArgoCD + SOPS + GitHub Actions" stack was pure hallucination.
- **Two production topologies exist in the same repo and they disagree** — `services/proxy/` is a single-server all-in-one (one Postgres, one Redis, no splits) while `services/ali/` splits into 3 separate Postgres + Redis containers per service, and `services/tx/` keeps only 3 static frontends. A deploy script (`scripts/deploy.sh:116-118`) hard-codes which topology a service belongs to, but the three topologies cannot be reconciled — the same service has different `PORT` values across them (e.g. `hamr-jiabu-api` is **3003** in `services/ali/docker-compose.yml:110` but **8082** in `services/proxy/nginx.conf:207`).
- **Secret handling is `.env`-only with no real defence in depth** — placeholder passwords in `services/proxy/.env.example:2,5,7` (`change_me_to_a_strong_password`), default Grafana password baked into 2 of 3 compose files (`services/proxy/docker-compose.yml:262`, `services/ali/docker-compose.yml:236` use `:admin` fallback), and `services/proxy/initdb/01-create-databases.sql` is mounted into Postgres with no separate role/grant.
- **Observability stack is real but minimal** — `monitoring/prometheus.yml` only scrapes `node-exporter` + `hamr-api-gateway` (2 jobs, 2 targets). `monitoring/alerts.yml` has 5 alert rules (CPU/Memory/Disk/NodeDown) — none for app, DB, HTTP, SSL expiry, backup freshness, certificate expiry or DNS. Grafana dashboard provisioning points to an empty folder (`monitoring/grafana/provisioning/dashboards/provider.yml:8-9` path is `/etc/grafana/provisioning/dashboards`, mounted read-only, but no `.json` files exist on disk).
- **Deploy/backup/health-check scripts are functional but lack the cross-cutting guards** expected of a 14-subproject platform — `scripts/backup.sh:24` only backs up a container named `hamr-postgres` (does not match the split `hamr-postgres-account|hamr-postgres-app|hamr-postgres-jiabu` in `services/ali/`), `scripts/health-check.sh:3` hard-codes one server IP, `scripts/restore.sh:39` lets an operator pipe an arbitrary `.sql.gz` into a running DB with no integrity check, and there is no rotation/cleanup of `access.log`/`error.log`.

## Findings

### IaC / topology

- [P0] **[topology-drift] Two production topologies (`services/proxy/` vs `services/ali/`) declare incompatible port maps for the same service** — `services/proxy/nginx.conf:207` (proxy jiabu → 8082) vs `services/ali/docker-compose.yml:110` (hamr-jiabu-api `PORT: 3003`) — A deploy to `ali/` would route jiabu through `proxy/nginx.conf:207` expecting `:8082` and 502. Pick one source of truth: either standardize on 3003 (matches `ali/`) or split into per-service config. The README claims a single topology (`README.md:127-138`) but the three `services/*/docker-compose.yml` files disagree on network model (`hamr-net` defined vs `external`), DB count (1 vs 3), and exposed ports. — **effort M** — **impact high**
- [P0] **[topology-drift] `services/ali/` uses `hamr-net: external: true` (`services/ali/docker-compose.yml:3-4`) but no `init`-time check verifies the external network exists with the right subnet/driver** — `services/ali/docker-compose.yml:1-4` vs `scripts/setup.sh:44` (`docker network create hamr-net` only on the same host) — On the ali host, the network is created locally and ali compose attaches to it. On a second node, the network must already exist. Add a preflight `docker network inspect hamr-net || create` in `scripts/deploy.sh` and add an `external: true` consistency check. — **effort S** — **impact high**

## Top 5 recommended next actions

1. **Pick one canonical topology and delete the other two** — the `services/{proxy,ali,tx}` triple is unsustainable. Recommend: keep `services/ali/` as canonical prod, deprecate `services/proxy/` to a `dev/` example, and `services/tx/` is already minimal.
