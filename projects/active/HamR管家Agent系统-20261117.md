## 🎯 项目概述

### 项目背景

HamR 管家（`PROJ-005`）到 2026-11-17 为止是一个**纯数据底座**：五维 CRUD API + P2P
同步 + Web3 DID 身份。整个 HamR 仓库家族（15 个子仓库）**没有任何一行 LLM 或 Agent 代码** ——
`hamr-jiabu` 是基于 if-then 的规则引擎，不是 Agent；`hamr-browser` 是无状态浏览器自动化，
没有推理、没有工具调用、没有记忆。

这带来一个产品定位上的空洞：

- 管家能**存**家庭数据，但不能**用**这些数据回答问题。用户还得自己去翻列表。
- JiaBu 能**算**幸福指数，但它是离线报表，不是能对话、能追问、能行动的管家。
- 家庭场景的核心诉求是「随口一问就有答案」+「主动提醒」，而这两件事都需要
  **大模型驱动的 Agent 层**，而不是加一个筛选器。

同时，HamR 全平台的立足点是「数据本地化 / 数据主权」（P2P 架构、无中心服务器）。
这意味着 Agent 层**不能是一个云端大脑** —— 家庭成员档案、健康信息、资产清单
一旦随提示词上云，产品最核心的承诺就破了。

本项目要补的正是这一层：**本地优先、模型可插拔**的 Agent 运行时。

### 项目目标

- 目标1：在 `hamr-app` 现有 Rust 后端内实现 Agent 运行时（不新建仓库，复用五维数据 API 与 P2P 同步）
- 目标2：模型来源可插拔 —— 本地模型（Ollama 等 OpenAI 兼容端点）为默认路径，云端模型为显式开启项
- 目标3：出网数据默认脱敏（成员姓名一致性替换 + 电话/邮箱/证件号屏蔽），保证「本地优先」承诺在云端路径上同样成立
- 目标4：Agent 只读家庭数据，不替用户改写五维数据
- 目标5：具备会话记忆与长期记忆，且记忆每轮回到模型上下文

### 项目价值

- **用户价值**：管家从「数据表格」变成「能问能答的家庭助手」，随口一问就得到基于真实家庭数据的答案
- **业务价值**：补上「人时事物境」与「幸福指数」之间的交互层 —— 这是 HamR 区别于普通备忘录类产品的核心
- **技术价值**：把「本地优先 LLM 架构」在 Rust 生产服务里跑通，包括脱敏边界、工具鉴权、失败关闭等一整套工程约束

## 📐 项目范围

### 包含的功能

- [x] **Provider 抽象**：单一 `LlmProvider` trait，本地与云端共用 OpenAI Chat Completions 协议
- [x] **本地优先默认**：`HAMR_AGENT_ENABLED` 默认关闭；默认 provider 为 local（Ollama `127.0.0.1:11434/v1`）
- [x] **PII 脱敏层**：姓名一致性替换（成员A/成员B）+ 电话/邮箱/证件号/卡号屏蔽，幂等
- [x] **工具集（只读）**：list_people / list_events / list_tasks / list_things / list_spaces / get_dashboard
- [x] **长期记忆**：Agent 专属记忆表 + `remember` 工具，记忆随每轮提示词回灌
- [x] **主循环**：思考 → 调工具 → 观察 → 结论，`max_steps` 有界保护，工具失败不中断整轮
- [x] **HTTP 端点**：`/api/v1/agent/*`（chat / status / sessions / memories），与业务路由同级鉴权
- [x] **JiaBu 边界接口**：`jiabu_score` 工具（需配置 `HAMR_JIABU_URL` 才暴露）
- [ ] **主动触发**：定时巡检（过期物品、临近日程、久未联系）→ 生成主动提醒
- [ ] **写工具与确认**：创建待办 / 登记日程（必须经用户显式确认，v2）
- [ ] **前端对话界面**：聊天面板 + 工具轨迹可视化
- [ ] **多模型对比评测**：本地小模型 vs 云端模型在同一批家庭问题上的准确率/耗时对比

### 明确不包含

- 不包含：训练/微调模型 —— 本项目只做推理编排
- 不包含：把五维数据整体向量化为知识库检索 —— v1 用工具直查更准确也更容易审计
- 不包含：多 Agent 编排 / 子 Agent 派生 —— v1 单 Agent + 工具，复杂度留到有真实需求时
- 不包含：语音交互 —— 独立排期
- 不包含：Agent 会话参与 P2P 同步 —— 会话是设备本地的对话上下文，不应在家庭设备间漫游
- 不包含：替换 JiaBu —— Agent 负责对话与行动编排，幸福指数量化仍归 JiaBu 规则引擎

### 关键设计约束

这几条是本项目的**不变量**，后续迭代不得破坏：

| 约束 | 理由 |
|------|------|
| Agent 默认关闭 | 与本仓库既有安全取向一致（hamr-browser 鉴权 fail-closed、Grafana 弱口令 fail-closed） |
| `family_id` 由服务端注入，不接受模型参数 | 模型被诱导传入别的 family_id 就会读到别人家数据 |
| 工具集默认只读 | Agent 能读的比直接调 API 少，就已经超出了「助手」的合理边界 |
| 脱敏发生在出网那一刻，库里存原文 | 本地 Agent 必须看到真名，否则给不出有用建议；云端才脱敏 |
| 步数上限 + 兜底回复 | 模型执着调工具时必须有界，且不能返回空回答 |
| API Key 不得出现在任何日志/Debug 输出 | 参照 `Config::shared_secret` 的既有做法 |

### ⚠️ 现有文档偏差说明

创建本项目时发现 `PROJ-005` 的文档与代码存在**实质偏差**，已在本轮修正：

| 项 | 旧文档（PROJ-005 / P2P 提案） | 实际代码（`origin/main`） |
|----|---------------------------|------------------------|
| 数据库 | SQLite（嵌入式） | **PostgreSQL**（`Cargo.toml` sqlx postgres feature、`migrations/*.sql`、`docker-compose.yml`） |
| P2P 同步 | CRDT / Automerge | **LWW + sync_log 日志表**（`handlers/sync.rs`） |
| 前端 | Electron 桌面端 / React Native 移动端 | **Vite + React Web**（`frontend/`） |
| 身份 | Web3 DID | DID 已实现（`did.rs`），但鉴权有 open / shared-secret / did 三档 |

含义：P2P 提案（2026-03-18）里的「零服务器、本地 SQLite、42 人周」目标实际已被
PostgreSQL + Docker 方案取代 —— 也就是说**当前架构已经不是纯本地无服务器形态**。
本项目选择「Agent 运行时跑在用户设备侧、与既有部署形态解耦」，
既不强行回滚数据库选型，也不假设纯本地。

## 📝 关键决策记录

### [2026-11-17] Agent 运行时落在 hamr-app 内，不新建仓库
- **背景**：可选方案是新建 `hamr-butler` 仓库，或在现有 `hamr-app` 内加模块
- **决策内容**：在 `hamr-app` 后端内实现 `src/agent/` 模块
- **决策原因**：五维数据 API、鉴权中间件、P2P 同步都在这里；新建仓库意味着跨进程调用自己刚建的服务，凭空增加一跳网络与一套鉴权
- **影响范围**：Agent 与五维数据同进程共享连接池，工具直查 SQL 而非走 HTTP
- **状态**：✅ 已落地

### [2026-11-17] 本地优先 + 模型可插拔，云端需显式开启且默认脱敏
- **背景**：HamR 定位是数据本地化；同时本地模型能力弱于云端，一刀切本地会牺牲可用性
- **决策内容**：默认 provider = local（Ollama）；切云端需 `HAMR_AGENT_ENABLED=true` + `HAMR_AGENT_PROVIDER=cloud` + `HAMR_AGENT_API_KEY`；云端默认脱敏，放开 PII 需额外 `HAMR_AGENT_ALLOW_PII=true`
- **决策原因**：把「数据出网」变成一个用户能看见、能控制的显式动作，而不是默认行为
- **影响范围**：脱敏层成为云端路径的强制关卡；配置项成为运维关注点
- **状态**：✅ 已落地

### [2026-11-17] 工具集 v1 只读
- **背景**：Agent 一旦能写，就能替用户改写家庭数据 —— 这是不可逆的信任透支
- **决策内容**：v1 工具全部只读，唯一可写的是 Agent 自己的长期记忆表
- **决策原因**：读操作可撤销、可审计；写操作一旦出错，用户难以察觉
- **影响范围**：写工具推迟到 v2，且必须经用户显式确认
- **状态**：✅ 已落地

### [2026-11-17] family_id 由服务端注入，不作为模型参数
- **背景**：如果 `family_id` 出现在工具 schema 里，模型可以被诱导传入别的家庭 ID
- **决策内容**：工具 schema 中不存在 `family_id` 参数，运行时由服务端从请求体固定注入
- **决策原因**：把越权边界从「模型是否听话」变成「接口结构上就不可能」
- **影响范围**：所有工具函数签名不含 family_id，由 `ToolContext` 提供
- **状态**：✅ 已落地

### [2026-11-17] 幸福指数仍归 JiaBu，Agent 通过工具调用
