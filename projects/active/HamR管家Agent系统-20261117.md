## 🎯 项目概述

### 项目背景

HamR 管家（`PROJ-005`）到 2026-11-17 为止是一个**纯数据底座**：五维 CRUD API + P2P
同步 + Web3 DID 身份。整个 HamR 仓库家族（15 个子仓库）**没有任何一行 LLM 或 Agent 代码** ——
`hamr-jiabu` 是基于 if-then 的规则引擎，不是 Agent；`hamr-browser` 是无状态浏览器自动化，
没有推理、没有工具调用、没有记忆。

这带来一个产品定位上的空洞：

- 管家能**存**家庭数据，但不能**用**这些数据回答问题。用户还得自己去翻列表。
- JiaBu 能**算**幸福指数，但它是离线报表，不是能对话、能追问、能行动的管家。
- 家庭场景的核心诉求是「随口一问就有答案」+「主动提醒」，而这两件事都需要
  **大模型驱动的 Agent 层**，而不是加一个筛选器。

同时，HamR 全平台的立足点是「数据本地化 / 数据主权」（P2P 架构、无中心服务器）。
这意味着 Agent 层**不能是一个云端大脑** —— 家庭成员档案、健康信息、资产清单
一旦随提示词上云，产品最核心的承诺就破了。

本项目要补的正是这一层：**本地优先、模型可插拔**的 Agent 运行时。

### 项目目标

- 目标1：在 `hamr-app` 现有 Rust 后端内实现 Agent 运行时（不新建仓库，复用五维数据 API 与 P2P 同步）
- 目标2：模型来源可插拔 —— 本地模型（Ollama 等 OpenAI 兼容端点）为默认路径，云端模型为显式开启项
- 目标3：出网数据默认脱敏（成员姓名一致性替换 + 电话/邮箱/证件号屏蔽），保证「本地优先」承诺在云端路径上同样成立
- 目标4：Agent 只读家庭数据，不替用户改写五维数据
- 目标5：具备会话记忆与长期记忆，且记忆每轮回到模型上下文

### 项目价值

- **用户价值**：管家从「数据表格」变成「能问能答的家庭助手」，随口一问就得到基于真实家庭数据的答案
- **业务价值**：补上「人时事物境」与「幸福指数」之间的交互层 —— 这是 HamR 区别于普通备忘录类产品的核心
- **技术价值**：把「本地优先 LLM 架构」在 Rust 生产服务里跑通，包括脱敏边界、工具鉴权、失败关闭等一整套工程约束

## 📐 项目范围

### 包含的功能

- [x] **Provider 抽象**：单一 `LlmProvider` trait，本地与云端共用 OpenAI Chat Completions 协议
- [x] **本地优先默认**：`HAMR_AGENT_ENABLED` 默认关闭；默认 provider 为 local（Ollama `127.0.0.1:11434/v1`）
- [x] **PII 脱敏层**：姓名一致性替换（成员A/成员B）+ 电话/邮箱/证件号/卡号屏蔽，幂等
- [x] **工具集（只读）**：list_people / list_events / list_tasks / list_things / list_spaces / get_dashboard
- [x] **长期记忆**：Agent 专属记忆表 + `remember` 工具，记忆随每轮提示词回灌
- [x] **记忆分层**（2026-11-20）：记忆分 fact / preference / rule 三层，提示词按「家规 → 偏好 → 事实」分层渲染；同一内容重复「记住」视为再次确认，偏好就地升级为家规（clue → rule），DB 层唯一索引保证不写重复行
- [x] **主循环**：思考 → 调工具 → 观察 → 结论，`max_steps` 有界保护，工具失败不中断整轮
- [x] **HTTP 端点**：`/api/v1/agent/*`（chat / status / sessions / memories），与业务路由同级鉴权
- [x] **JiaBu 边界接口**：`jiabu_score` 工具（需配置 `HAMR_JIABU_URL` 才暴露）
- [x] **主动提醒内核**（2026-11-20）：三态决策（告知 / 稍后跟进 / 保持沉默）+ 闸门（免打扰时段、每日条数上限、紧急旁路、去重）；规则驱动扫描五维数据（临期物品、临近日程、逾期待办），**全程不调用模型**；手机屏消息格式（第一行结论 + 事实 + 唯一动作）
- [ ] **主动提醒调度与推送**：定时巡检触发 + 推送通道（内核已就绪，调度器与推送下一阶段接）
- [x] **家庭 Wiki**（2026-11-20）：五维数据的**确定性派生物** —— 实体页 + 页内分节 + 来源引用 + append-only 变更日志，由应用侧重建器写入，**模型只读不可写**
- [x] **场景包 Skills**（2026-11-20）：版本化不可变的 `SKILL.md`（frontmatter：name / description / version / tools），目录进提示词、正文按需加载；`tools` 白名单只用于**收敛**工具面，不构成授权
- [x] **审批写操作**（2026-11-20）：模型只能「提议」（`propose_task` / `propose_event`），落库走带成员鉴权的 HTTP 端点确认，`operation_id` 幂等；**工具表里没有 confirm**
- [x] **模型体检 Model Probe**（2026-11-20）：两道题判定「会不会调工具」「会不会用工具结果」，输出 0-3 分 + usable/degraded/unsupported + 行动建议；全程不碰真实数据
- [x] **成员维度会话**（2026-11-20）：`agent_sessions.member_id` 让会话归属具体成员；`member_id` 由服务端注入，不接受模型参数
- [ ] **前端对话界面**：聊天面板 + 工具轨迹可视化
- [ ] **多模型对比评测**：本地小模型 vs 云端模型在同一批家庭问题上的准确率/耗时对比

### 明确不包含

- 不包含：训练/微调模型 —— 本项目只做推理编排
- 不包含：把五维数据整体向量化为知识库检索 —— v1 用工具直查更准确也更容易审计
- 不包含：多 Agent 编排 / 子 Agent 派生 —— v1 单 Agent + 工具，复杂度留到有真实需求时
- 不包含：语音交互 —— 独立排期
- 不包含：Agent 会话参与 P2P 同步 —— 会话是设备本地的对话上下文，不应在家庭设备间漫游
- 不包含：替换 JiaBu —— Agent 负责对话与行动编排，幸福指数量化仍归 JiaBu 规则引擎
- 不包含：多 Agent 协作（Linger 的 Rooms / `team.md`）—— 无真实需求，复杂度与安全面双增
- 不包含：桌面 / 浏览器自动化 —— 与「结构化只读工具」定位冲突，浏览器自动化由 `hamr-browser`（PROJ-014）另立项目
- 不包含：语音交互 —— 独立排期
- 不包含：后台任务克隆 —— 长任务引入并发会话与成本失控，v1 在对话主循环内解决
- 不包含：模型自改写自身提示词 —— 不可审计；只做确定性的规则巩固（clue → rule）

### 关键设计约束

这几条是本项目的**不变量**，后续迭代不得破坏：

| 约束 | 理由 |
|------|------|
| Agent 默认关闭 | 与本仓库既有安全取向一致（hamr-browser 鉴权 fail-closed、Grafana 弱口令 fail-closed） |
| `family_id` 由服务端注入，不接受模型参数 | 模型被诱导传入别的 family_id 就会读到别人家数据 |
| 工具集默认只读 | Agent 能读的比直接调 API 少，就已经超出了「助手」的合理边界 |
| 脱敏发生在出网那一刻，库里存原文 | 本地 Agent 必须看到真名，否则给不出有用建议；云端才脱敏 |
| 步数上限 + 兜底回复 | 模型执着调工具时必须有界，且不能返回空回答 |
| API Key 不得出现在任何日志/Debug 输出 | 参照 `Config::shared_secret` 的既有做法 |
| 写操作默认关闭，且必须经人显式确认 | 写是不可逆的信任透支；提议与批准必须分离 |
| 模型不能批准自己的写操作 | 工具表里没有 confirm/approve —— 边界要落在接口结构上，不是提示词上 |
| 技能不授权 | 技能包只是提示词，只能收敛工具面；服务端对每个工具逐一鉴权 |
| Wiki 页面模型不可写 | 唯一写者是重建器 —— 避免模型编造的家庭事实被固化成知识 |
| `member_id` 由服务端注入 | 与 `family_id` 同理：模型不能自称是别人 |

## 🛠 技术方案

### 技术栈

- **语言**：Rust 2021（与 `hamr-app` 后端一致，不引入第二套后端）
- **框架**：axum 0.7（复用现有路由与中间件）
- **模型协议**：OpenAI Chat Completions（本地 Ollama 与云端 API 同协议，一套实现通吃）
- **HTTP 客户端**：reqwest 0.12（native-tls，与 Dockerfile 的 `libssl-dev` 保持一致）
- **脱敏**：regex 1.13 + 一致性别名映射
- **数据库**：PostgreSQL（沿用 `hamr-app` 现有栈；⚠️ 见下方偏差说明）
- **存储抽象**：`ConversationStore` trait —— 生产用 `PgStore`，测试用 `MemStore`

### ⚠️ 现有文档偏差说明

创建本项目时发现 `PROJ-005` 的文档与代码存在**实质偏差**，已在本轮修正：

| 项 | 旧文档（PROJ-005 / P2P 提案） | 实际代码（`origin/main`） |
|----|---------------------------|------------------------|
| 数据库 | SQLite（嵌入式） | **PostgreSQL**（`Cargo.toml` sqlx postgres feature、`migrations/*.sql`、`docker-compose.yml`） |
| P2P 同步 | CRDT / Automerge | **LWW + sync_log 日志表**（`handlers/sync.rs`） |
| 前端 | Electron 桌面端 / React Native 移动端 | **Vite + React Web**（`frontend/`） |
| 身份 | Web3 DID | DID 已实现（`did.rs`），但鉴权有 open / shared-secret / did 三档 |

含义：P2P 提案（2026-03-18）里的「零服务器、本地 SQLite、42 人周」目标实际已被
PostgreSQL + Docker 方案取代 —— 也就是说**当前架构已经不是纯本地无服务器形态**。
本项目选择「Agent 运行时跑在用户设备侧、与既有部署形态解耦」，
既不强行回滚数据库选型，也不假设纯本地。

## 📝 关键决策记录

### [2026-11-17] Agent 运行时落在 hamr-app 内，不新建仓库
- **背景**：可选方案是新建 `hamr-butler` 仓库，或在现有 `hamr-app` 内加模块
- **决策内容**：在 `hamr-app` 后端内实现 `src/agent/` 模块
- **决策原因**：五维数据 API、鉴权中间件、P2P 同步都在这里；新建仓库意味着跨进程调用自己刚建的服务，凭空增加一跳网络与一套鉴权
- **影响范围**：Agent 与五维数据同进程共享连接池，工具直查 SQL 而非走 HTTP
- **状态**：✅ 已落地

### [2026-11-17] 本地优先 + 模型可插拔，云端需显式开启且默认脱敏
- **背景**：HamR 定位是数据本地化；同时本地模型能力弱于云端，一刀切本地会牺牲可用性
- **决策内容**：默认 provider = local（Ollama）；切云端需 `HAMR_AGENT_ENABLED=true` + `HAMR_AGENT_PROVIDER=cloud` + `HAMR_AGENT_API_KEY`；云端默认脱敏，放开 PII 需额外 `HAMR_AGENT_ALLOW_PII=true`
- **决策原因**：把「数据出网」变成一个用户能看见、能控制的显式动作，而不是默认行为
- **影响范围**：脱敏层成为云端路径的强制关卡；配置项成为运维关注点
- **状态**：✅ 已落地

### [2026-11-17] 工具集 v1 只读
- **背景**：Agent 一旦能写，就能替用户改写家庭数据 —— 这是不可逆的信任透支
- **决策内容**：v1 工具全部只读，唯一可写的是 Agent 自己的长期记忆表
- **决策原因**：读操作可撤销、可审计；写操作一旦出错，用户难以察觉
- **影响范围**：写工具推迟到 v2，且必须经用户显式确认
  （⚠️ 已被 [2026-11-20] 审批写操作决策取代：工具集仍只读，但写路径已以「模型提议 → 人工确认」两阶段落地）
- **状态**：✅ 已落地（写路径部分已被后续决策取代）

### [2026-11-17] family_id 由服务端注入，不作为模型参数
- **背景**：如果 `family_id` 出现在工具 schema 里，模型可以被诱导传入别的家庭 ID
- **决策内容**：工具 schema 中不存在 `family_id` 参数，运行时由服务端从请求体固定注入
- **决策原因**：把越权边界从「模型是否听话」变成「接口结构上就不可能」
- **影响范围**：所有工具函数签名不含 family_id，由 `ToolContext` 提供
- **状态**：✅ 已落地

### [2026-11-17] 幸福指数仍归 JiaBu，Agent 通过工具调用
- **背景**：Agent 与 JiaBu 都涉及「分析家庭数据」，存在职责重叠风险
- **决策内容**：Agent 负责对话与行动编排；幸福指数量化评分保留在 JiaBu 的规则引擎，Agent 通过 `jiabu_score` 工具调用
- **决策原因**：两套评分口径并存会让用户看到互相矛盾的数字
- **影响范围**：JiaBu 地址未配置时不暴露该工具，避免给出「工具不可用」的噪声
- **状态**：✅ 已落地

### [2026-11-20] Linger 不作代码基座，只作架构模式参照系
- **背景**：需要为家庭场景 Agent 选基座路线；Linger（simplexai-labs/linger）是当前热度较高的本地个人 Agent 开源项目
- **决策内容**：保持 Rust 自研运行时；不 fork、不引依赖、不 sidecar 部署 Linger；按调研提案分阶段借鉴其主动提醒、记忆分层、技能包、幂等审批四个模式
- **决策原因**：四重不匹配 —— ① 许可：自定义非 OSI 条款禁止向本组织外提供托管服务；② 技术栈：Go + Node + Electron vs Rust 单进程；③ 定位：单用户个人产品，无家庭多租户模型；④ 能力模型：桌面自动化 vs 结构化只读工具。其领先部分集中在产品机制，重实现成本低于集成成本，且不破坏既有安全不变量
- **影响范围**：本轮已落地主动提醒与记忆分层两项借鉴；技能包与幂等审批推迟到写工具阶段
- **复审条件**：Linger 若改为 OSI 许可，或发布无 Electron/CLI 依赖的独立可嵌入 Agent 核心库，则重新评估
- **状态**：✅ 已落地

### [2026-11-20] 主动提醒走规则驱动，不经过模型
- **背景**：主动提醒要么用模型判断「该不该说」，要么用规则判断；前者更灵活但会把家庭数据送出网、且受提示词注入影响
- **决策内容**：主动提醒的**判定**全部由规则完成（信号来自五维数据表 + 纯函数闸门），消息文案也由规则拼装；模型不参与
- **决策原因**：主动提醒是「系统主动打扰用户」，风险等级高于被动问答。规则路径不出网、不涉脱敏、行为可预测可审计，且不会被写进家庭数据的恶意指令操纵。LLM 润色文案可作为未来可选项，但必须走云端脱敏路径
- **影响范围**：`src/agent/proactive.rs` 与对话主循环完全解耦；新增独立端点与两张表
- **状态**：✅ 已落地

### [2026-11-20] 家庭 Wiki 是五维数据的确定性派生物，不做连接器灌入
- **背景**：Linger 的 Personal Wiki 由 Gmail / Slack / 日历连接器夜里灌入，模型提议 + 应用校验后落库；HamR 已有五维结构化数据底座
- **决策内容**：家庭 Wiki 由**应用侧重建器**从五维数据确定性生成，模型只读不可写；每节带来源引用，改动进 append-only 变更日志；重建幂等
- **决策原因**：再灌一个 Wiki 等于建两套事实源，必然漂移；而模型写 Wiki 会把幻觉固化成「知识」。事实的权威所在只能是五维表
- **影响范围**：`src/agent/wiki.rs` + `agent_wiki_*` 四张表；代价是「上周因为接送时间吵了一架」这类叙事记忆装不下，归记忆层与会话
- **状态**：✅ 已落地

### [2026-11-20] 写操作的确认走 HTTP 端点，不做成模型工具
- **背景**：Agent 要能「办事」（建待办、登日程），但写操作出错后成员往往难以察觉
- **决策内容**：模型只能「提议」；真正落库由客户端在成员鉴权上下文下调 HTTP 端点完成；`operation_id` 由服务端生成并作幂等键；**工具表里永远没有 approve / confirm 类工具**
- **决策原因**：如果工具表里有 `confirm_write`，模型就同时握有提议与批准两把钥匙 —— 任何写在家庭数据里的注入指令都可能诱导模型自我批准。提示词是建议，不是边界；边界必须落在接口结构上
- **影响范围**：`src/agent/writeops.rs` + `agent_write_ops` 表；写操作默认关闭（`HAMR_AGENT_ALLOW_WRITE`），提议与批准分离
- **状态**：✅ 已落地

### [2026-11-20] 技能包只引导，不授权
- **背景**：不同家庭场景需要不同的问法与话术边界，塞进一个系统提示词会让提示词臃肿、场景串味
- **决策内容**：场景包是版本化不可变的 `SKILL.md`（目录进提示词、正文按需加载）；`tools` 白名单只用于**收敛**暴露给模型的工具面，服务端对每个工具仍独立鉴权；v1 技能包不含可执行脚本
- **决策原因**：沿用 Linger 的核心原则「A skill guides an agent. It does not give the agent any permission.」—— 技能包是提示词，不是权限；且不执行模型可控代码，与既有安全取向一致
- **影响范围**：`src/agent/skills.rs` + `agent_skills` 表 + `backend/skills/` 目录
- **状态**：✅ 已落地
