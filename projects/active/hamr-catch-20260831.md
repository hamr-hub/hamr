## 🎯 项目概述

### 项目背景
家庭场景下，资产（电器、收藏、日用品、证件等）信息散落在多个家庭成员的脑海中或纸质记录中，难以集中盘点、追溯与备份。现有的云端 SaaS 方案存在隐私外泄、订阅费用、网络依赖等问题。本项目用 **纯局域网 P2P** 的思路：完全去掉中心服务器，所有数据只存在家庭成员的手机 / iPad 本地，设备间通过 WebRTC 局域网直连互通。

### 项目目标
- 目标1：基于 PWA 提供资产录入、查看、编辑、筛选的本地台账能力
- 目标2：通过 WebRTC 实现同一 WiFi 下多设备（手机 ↔ iPad ↔ 手机）资产记录 P2P 同步
- 目标3：拍照仅本地保存，缩略图跨设备同步，原图按需点对点传输
- 目标4：离线可用，断网仍可录入，回到局域网自动同步
- 目标5：JSON / Excel 导出，便于手动备份到任意网盘
- 目标6：用 Rust 写一个"零依赖"的极简局域网静态文件服务，仅分发网页，不存任何业务数据

### 项目价值
- **用户价值**：零服务器、零公网、零订阅费，隐私完全本地化
- **业务价值**：丰富 HamR 家庭场景应用矩阵，验证 P2P 架构可行性
- **技术价值**：探索"无信令服务器"的纯局域网 P2P 工程实践，沉淀前端 + Rust 联动的工程模板

## 🛠 技术方案

### 技术栈
- **本地服务**：Rust（stdlib only，无任何外部依赖），二进制 < 1 MB
- **PWA**：纯 HTML + 原生 JS + Tailwind（CDN），零构建步骤
- **本地数据库**：IndexedDB（Dexie 风格封装）
- **P2P 通信**：WebRTC DataChannel + 手写 SDP/ICE 直连（局域网内）
- **设备发现**：QR 二维码（qrcode.js + html5-qrcode）
- **图片处理**：Canvas 前端 resize + toBlob
- **导出**：SheetJS（xlsx）+ JSON.stringify
- **PWA 安装**：manifest.json + Service Worker（手写）

### 架构设计

```
[设备 A 手机]                    [设备 B iPad]
   |                                 |
   | Rust 服务 (分发静态页面)          |
   |<----- HTTP ---- [192.168.x.x:8080]
   |                                 |
   | WebRTC DataChannel (LAN 直连)
   |<============== P2P =============>|
   |                                 |
IndexedDB                        IndexedDB
(本地资产+缩略图)                  (本地资产+缩略图)
   |                                 |
图片原图                           图片原图
(永远只在拍照设备)
```

### 关键技术决策
1. **QR 握手而非 mDNS**：mDNS 在浏览器 WebRTC 中无法获取 IP；QR 是真正零依赖方案，扫码即配对
2. **Rust 用 stdlib 而非 tiny_http / warp**：离线 / 受限网络下 cargo 拉不到依赖，stdlib 方案可一次编译永久运行
3. **缩略图同步而非原图**：家庭场景每户几十~几百件物品，原图动辄几百 MB，缩略图（5-15 KB/张）即可用
4. **冲突解决 LWW + 快照**：用户体验简单，时间较新版本胜出，旧版本入 `conflicts` 表备查
5. **零服务业务逻辑**：Rust 服务只分发 HTML/JS/CSS/manifest/sw.js，不接触任何业务数据

## 📝 关键决策记录

### [2026-08-31] 用 stdlib 实现 Rust 服务
- **背景**：crates.io 网络环境受限，无法 `cargo add` 依赖
- **决策内容**：用 `std::net::TcpListener` + `std::fs` 手写极简 HTTP 服务，无任何外部 crate
- **决策原因**：确保一次 `rustc` 编译即可永久运行，避免家庭环境下的网络依赖
- **影响范围**：服务实现本身略增代码量（约 150 行），但彻底摆脱网络依赖

### [2026-08-31] 采用 QR 握手而非 mDNS
- **背景**：WebRTC 直连需要 SDP/ICE 信令；mDNS 在浏览器不可用
- **决策内容**：采用方案 A：QR 码握手 + 手动输入 IP fallback
- **决策原因**：零依赖、零配置；适合家庭"低频配对"场景
- **影响范围**：每对设备首次配对需扫一次码（≈ 30 秒），之后自动重连
