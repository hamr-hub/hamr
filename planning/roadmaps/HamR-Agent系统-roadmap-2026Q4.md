## 🎯 产品愿景与战略

### 产品愿景

让 HamR 从「记录家庭数据的工具」变成「懂这个家的管家」——
用户随口一问，答案基于这个家真实的数据；家里的事，管家会主动提醒。

### 战略目标

1. **能力可用**：本地 7B 级模型能稳定完成「查数据 → 给建议」的完整闭环
2. **隐私不打折**：接云端模型时，成员姓名与联系方式默认不出网
3. **交互成型**：前端有像样的对话界面，用户能看懂 Agent 依据什么给出的建议

### 核心指标

| 指标 | 当前值 | 目标值 | 达成时间 |
|------|--------|--------|---------|
| 评测集工具调用准确率 | 未测 | ≥ 80%（本地 7B） | 2026-12-31 |
| 端到端响应延迟（本地） | 未测 | ≤ 8s | 2026-12-31 |
| 云端路径 PII 泄漏用例 | 0 | 始终 0 | 持续 |
| Agent 端点鉴权覆盖率 | 100% | 100% | 已达成 |
| 单元测试通过率 | 100% | 100% | 持续 |

## ⚠️ 风险与依赖

### 主要风险

| 风险 | 影响范围 | 缓解措施 | 负责人 |
|------|---------|---------|-------|
| 本地小模型工具调用能力弱 | 端到端联调、评测 | 提示词强化；评测集量化；必要时上云端 | 技术负责人 |
| 脱敏后语义损失导致建议变差 | 云端路径 | 一致性别名保留区分度；`ALLOW_PII` 逃生阀 | 开发工程师 |
| 慢模型调用占用服务资源 | 全部 API | 超时 + 步数上限；对话与数据端点分离 | 开发工程师 |
| 前端交互拖慢主节奏 | 前端面板 | 先做可用原型，不追求完整设计 | 开发工程师 |
| 评测集缺真实家庭样本导致偏差 | 评测基线 | 用 PROJ-005 现有五维数据构造合成家庭 | 测试工程师 |

### 外部依赖

- Ollama 或本地模型运行时：用户自备 | 影响本地联调
- 云端模型 API（可选）：用户自备 Key | 仅在选云端时产生
- PROJ-012 JiaBu：幸福指数接口 | 未就绪时 `jiabu_score` 工具不暴露，不阻塞主线

### 假设条件

- `hamr-app` 的五维数据表结构保持稳定（Agent 工具直查这些表）
- `hamr-app` 继续沿用 PostgreSQL（不迁回 SQLite）
- 团队规模维持现状

## 📈 成功指标

### 技术指标

- 评测集工具调用准确率：≥ 80%（本地 7B）/ ≥ 95%（云端）
- 端到端响应延迟：本地 ≤ 8s，云端 ≤ 3s
- Agent 端点鉴权覆盖率：100%（与业务路由同级）
- 云端 PII 泄漏用例：0
- cargo test 通过率：100%

### 产品指标

- 主动提醒采纳率（用户点击/确认比例）：≥ 30%
- 连续使用天数（次周留存）：≥ 40%
- 家庭问答覆盖：常见问题（今天有什么安排 / 谁生日 / 有什么快过期）均有准确回答

## 🔄 调整机制

### 双周评审

- **周期**：每两周一次
- **内容**：评测准确率变化、风险清单、优先级调整

### 指标驱动调整

- 准确率连续两周低于 60% → 优先做提示词调优，不进入新功能
- 出现任一 PII 泄漏 → 立即回滚云端路径功能，优先级高于一切
- 评测集无法覆盖新场景 → 先补评测再开发
