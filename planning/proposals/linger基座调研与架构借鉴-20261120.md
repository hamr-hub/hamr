# Linger 基座调研与架构借鉴

## 📋 调研信息

| 项 | 内容 |
|---|---|
| 调研对象 | [simplexai-labs/linger](https://github.com/simplexai-labs/linger)（v1.x，main 分支，2026-11 快照） |
| 调研问题 | Linger 是否适合作为 HamR 家庭管理类 Agent 的**基座**？ |
| 调研日期 | 2026-11-20 |
| 关联项目 | PROJ-019（HamR 管家 Agent 运行时）、PROJ-016（家庭关系修复 Agent） |
| 结论摘要 | **不作为代码基座；作为架构模式参照系，分阶段借鉴其主动提醒、记忆分层与技能包机制** |

## 🎯 结论（一句话）

Linger 是一个**完整的个人 AI 助理产品**，不是可嵌入的 Agent 框架：技术栈（Go/Node/Electron）、许可（自定义非 OSI、禁止对外托管）、执行模型（编排 `claude -p` 等编码 Agent 子进程做桌面自动化）和单用户个人定位，四条都与 HamR「Rust 单进程、家庭多租户、只读结构化工具、本地优先」的既定架构冲突。但它在**主动性、记忆工程、技能打包**三件事上的产品设计成熟度明显领先，恰好覆盖 PROJ-019 尚未开工的三个里程碑，值得按模式借鉴（不抄代码、不引依赖）。

## 🔍 Linger 是什么

- 定位：「本机运行的 Claude 级个人 Agent」，1.7k stars，活跃开发中（526 commits，35 open PRs）。
- 技术栈（monorepo，pnpm workspaces）：
  - **TeamHub**：Go（Gin）+ PostgreSQL 17 + River 任务队列；房间、文档、权限、历史。
  - **node-services**：Node.js 26（Hono），承载 Agent Service / Memory / LLM Wiki。
  - **Web**：React 19 + Vite；**Desktop**：Electron；**Computer Daemon**：Go + SQLite。
  - 语音 LiveKit、桌面操作 Cua + Playwright、连接器 Composio、协作文档 BlockNote/Yjs。
- Agent 执行方式：本机以**子进程协议适配**启动编码 Agent CLI（Claude `stream-json`、Codex `app-server`、Pi RPC），经单一 WebSocket 由守护进程编排；**官方明确没有可嵌入的 Agent loop SDK / 稳定 API**，扩展面只有 OpenAPI 契约、teamhub CLI、per-run MCP、Markdown 技能包。
- 模型层：自带 PolyStrata MoE 分层推理（GPU→RAM→SSD 卸载专家），也支持 llama.cpp 与自带订阅；模型流量不经过其服务器。
- 代表特性：个人 wiki（实体页 + 来源引用 + 变更日志，LoCoMo 自称 95 分）、主动 Agent、「Dreaming」夜间自我改进、Agent 团队（team.md）、语音会议、桌面/浏览器自动化。

## ❌ 为什么不适合作为 HamR 的代码基座

| # | 冲突点 | 具体事实 | 对 HamR 的影响 |
|---|--------|---------|---------------|
| 1 | **它是产品，不是框架** | Agent loop 编排在 Electron/守护进程里，依赖编码 Agent CLI（`claude -p` 等）作为「运行时」；无 SDK、无嵌入 API | HamR 要的是 axum 内一个 `src/agent/` 模块，引入它等于扛回整套桌面产品 |
| 2 | **许可不是 OSI 开源** | 自定义「Co-Workpace Open Source License」（Apache-2.0 + 附加条款）：**禁止向本组织之外的人提供托管/管理服务**，违者需商业授权；前端 LOGO/版权不可移除 | HamR 面向家庭用户的任何服务化形态（哪怕替亲友运维一套）都可能落入「third-party hosted service」，法律不确定性不可接受 |
| 3 | **技术栈不兼容** | Go + Node 26 + React/Electron + Postgres17 + River；HamR 后端是 Rust + axum 单进程 | 无法嵌入；sidecar 部署要求家庭设备跑 Docker 全家桶 + 16GB 起内存，违背轻量本地部署 |
| 4 | **单用户个人模型** | 「Another Me」单一 owner，记忆、权限、连接器全部围绕一个人；文档无任何家庭/多租户章节 | HamR 的核心不变量是 `family_id` 服务端注入的家庭多租户隔离，需要二次改造其权限模型 |
| 5 | **Agent 能力模型不同** | Linger Agent 靠 Cua 点桌面 UI、Playwright 操作用户已登录的 Chrome、Shell 以用户权限执行命令；技能可携带 scripts | HamR v1 是结构化只读工具直查 SQL、明确不执行模型生成的代码（提示词注入防御）。桌面自动化恰是 HamR 有意推迟的方向（hamr-browser 另立项目） |
| 6 | **数据连接方式不同** | 个人数据靠 Gmail/Slack/Outlook/日历连接器夜间灌入 wiki | HamR 已有「人时事物境」五维结构化数据底座，灌 wiki 是重复建设且丢失结构 |

**PolyStrata 的定位**：它是 MoE 模型推理引擎（解决「大模型如何塞进小显存」），与 Agent 框架正交。HamR 已选择「用户自备 Ollama / 任意 OpenAI 兼容端点」，不捆绑推理实现。PolyStrata 可作为**未来本地模型加速选项持续观察**（独立仓库，许可另查），不影响本次决策。

## ✅ 值得借鉴的四个模式

以下均为**机制/产品设计层面的借鉴**，由 HamR 在 Rust 运行时内重新实现，不引入其代码与依赖。

### 1. 主动提醒的「三态决策 + 闸门」（对应 PROJ-019 主动提醒里程碑）

Linger 主动 Agent 的设计，直接解答了 PROJ-019 风险表中「主动提醒会不会变成骚扰」：

- 每个事件独立跑一轮，三态结果：**立即告知 / 稍后跟进 / 保持沉默**。
- 闸门（Gate）：免打扰时段（夜间转跟进）、**每日条数上限**、**紧急旁路**（如取消事件不受夜间限制）、**去重**（同一事项同一状态每天只判一次）、对话安静后才投递。
- 消息为手机屏设计：第一行结论，中间事实，结尾**唯一动作**，无废话。
- 反馈学习：只对「Agent 主动发起的消息」的回复做学习；一次偏好 = 线索（clue，不改变行为），同类第二次 = 规则（rule），用户显式点名类别 = 立即成规则；规则「少而宽」，夜间重写，新偏好覆盖旧规则。

**HamR 落地（本轮已实现内核）**：`src/agent/proactive.rs`
- 纯函数 `decide()` 实现闸门：免打扰（支持跨午夜）、日上限、紧急旁路、去重；
- 规则驱动扫描（不依赖 LLM、不出网、天然不涉脱敏）：临期物品（`things.expiry_date`）、临近日程（`events.start_time`）、逾期高优待办（`tasks`）；
- 持久化 `agent_reminders` + `agent_proactive_log`，提供手动扫描 HTTP 入口（定时调度与推送通道下一阶段接）；
- clue→rule 学习落到记忆子系统（见下）。

### 2. 记忆分层：偏好/规则 ≠ 事实，摘要索引 ≠ 全量回灌

Linger 把记忆分成**个人 wiki**（实体页、每条事实来源引用、模型提议逐条校验、应用侧追加变更日志）与 **Agent 记忆**（偏好、流程、教训；先给摘要索引、详情按需取），且写入都在**对话安静后的后台串行任务**里完成，不在说话时拖慢响应。

对照 HamR 现状：`agent_memories` 是一张扁平表，最多 20 条**每轮全量塞进系统提示词**，无类型、无巩固、无淘汰 —— 家庭用得越久，提示词越肿、冲突记忆越多。

**HamR 落地（本轮）**：
- 记忆加 `kind`（`fact` / `preference` / `rule`）与 `importance`、`reinforced_count`；
- 提示词分层渲染：家规（rule）→ 偏好（preference）→ 事实（fact），按重要度截断；
- `remember` 工具接受 kind；**重复记忆第二次自动把 preference 巩固为 rule**（clue→rule 的最小实现）；
- 仍保持「记忆每轮回灌」这一 PROJ-019 既定目标，仅改分层与排序。

**后续阶段**：候选记忆 → 后台巩固（extract/consolidate/recall 三阶段）、冲突记忆失效、事实类记忆改为工具按需检索（对应 wiki 层），在评测集验证提示词长度与命中率后再做。

### 3. 技能包机制（对应 PROJ-016 等家庭场景 Agent）

Linger 的 Skill = 一个含 `SKILL.md`（YAML frontmatter：`name` + 给模型看的 `description`）的目录，可带 `references/`、`scripts/`；**版本化、不可变**（发布后不可原地改，只能发新版本 + catalog 登记）。最关键的一条原则：

> **技能只「引导」Agent，不授予任何权限；每个动作仍由服务端逐一鉴权。**

这与 HamR「family_id 服务端注入、工具集只读」的不变量哲学完全一致，可直接用来设计家庭场景包（关系修复话术、节庆提醒、育儿协商等）：

**后续阶段（建议）**：
- 在 hamr-app 内设计 `scenarios/`（或 `skills/`）目录：每个场景一个版本化 Markdown 包（系统提示词片段 + 允许工具白名单）；
- 加载后向模型多暴露一个 `use_skill` 选择机制，或首轮由 family 配置启用；
- 工具权限在服务端按包的白名单收敛（技能不给授权，但可以声明「只用这些」），结构上保证场景包不能越权；
- PROJ-016（家庭关系修复 Agent）作为第一个消费方。

### 4. 写操作幂等与审批（对应 PROJ-019 v2 写工具）

- teamhub CLI 写操作带幂等 `--operation-id`，服务端去重；
- 敏感动作（发邮件等）必须经用户批准，权限可审计、可复查。

**后续阶段**：v2 写工具（创建待办/登记日程）落地时，引入：
- 客户端生成 `operation_id`，服务端幂等落库；
- 两阶段：`propose`（预览 diff）→ 用户确认 → `commit`；
- 审批记录入 `agent_proactive_log` 同款审计表。

## 🧭 其余观察（暂不动作）

- **Model Autopilot**（探测硬件→选模型→真提问验证）：PROJ-019 风险表首位就是「7B 工具调用弱」。未来可做 `/api/v1/agent/status` 之外的模型探测向导：对 Ollama 跑一道工具调用样例题，不达标则推荐更大模型或云端。列入评测集里程碑之后。
- **team.md 多 Agent 协作**：PROJ-019 已明确 v1 不做多 Agent，维持。
- **个人 wiki 的来源引用与变更日志**：家庭事实未来允许 Agent 写入时（v2+），「每条事实引用来源消息 + 应用侧 append-only 变更日志」是防幻觉的好设计，提前记录。
- Linger 的夜间任务依赖付费编码 Agent 订阅，账单按订阅走且本地模型会明显变慢 —— 这也是它不适合家庭低成本部署的侧证。

## 📌 决策记录

### [2026-11-20] 不采用 Linger 作为代码基座，仅作模式参照
- **背景**：需要为 PROJ-019 选择基座路线；Linger 是当前热度较高的本地个人 Agent 开源项目。
- **决策**：保持 Rust 自研运行时；不 fork、不引依赖、不 sidecar 部署 Linger；按本提案分阶段借鉴其主动提醒、记忆分层、技能包、幂等审批四个模式。
- **决策原因**：许可（禁第三方托管）、栈（Go/Node/Electron vs Rust）、定位（产品非框架、单用户）、能力模型（桌面自动化 vs 结构化只读工具）四重不匹配；而其领先部分主要是产品机制，重新实现的成本低于集成成本，且不破坏既有安全不变量。
- **复审条件**：若 Linger 未来（a）改为 OSI 许可，（b）发布独立可嵌入的 Agent 核心库（无 Electron/CLI 依赖），可重新评估。
